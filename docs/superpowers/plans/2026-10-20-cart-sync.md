# Cart Sync and In-Chat Buying Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Shoppers pick variants, add to cart, edit the cart and reach checkout from the chat widget, with the widget's cart and the Ranger theme's cart always showing the same state.

**Architecture:** One cart store in the widget holds the last cart Shopify confirmed. Widget writes go through a serial queue to the AJAX Cart API with the `sections` parameter, so one answer updates both the theme's HTML and the store in the same synchronous block. Theme writes are seen by wrapping `fetch`/XHR; back/forward, tab focus and other tabs trigger a re-read.

**Tech Stack:** React 18 (`useSyncExternalStore`), TypeScript, Vite IIFE bundle, Shopify AJAX Cart API and Section Rendering API, vitest, happy-dom (new dev dependency).

**Spec:** `docs/superpowers/specs/2026-10-20-cart-sync-design.md`

## Global Constraints

- Shopify owns the cart: the cookie cart through the AJAX Cart API is the only source of truth. No Storefront API cart.
- Confirmed updates only: the UI never shows a cart state Shopify did not return.
- Every storefront URL goes through `ROOT` (`window.Shopify?.routes?.root || "/"`) from `chat-widget/src/urls.ts`.
- Interception never changes a theme request or response and never throws into the theme.
- Theme specifics live only in `chat-widget/src/cart/ranger.ts`. Ranger values are read from the theme (Task 9), never guessed.
- The server never reads or writes the cart. No changes to the agent prompts.
- New user-facing strings go in both `chat-widget/src/locales/en.json` and `it.json`.
- Commits: Conventional Commits, no `Co-Authored-By` trailer (project `CLAUDE.md`).
- Spec deviation: `ajax.ts` has no `update` call. Nothing in Part 1 uses it (YAGNI). Theme `update.js` writes are still intercepted.

## Review Focus

1. **Locale-prefixed storefront** (`ROOT = "/it/"`): theme requests to `/it/cart/change.js` must be recognised, and widget requests must go to `/it/cart/...`. Tests in Tasks 2 and 5.
2. **Theme add with a non-JSON response** (a form-encoded `fetch` to `/cart/add` that answers with HTML or a redirect): the widget must still re-read the cart. Test in Task 5.
3. **A refused write in the middle of rapid taps** (+ + + where the second gets a 422): the queue must keep running the rest and the error must stay on that line. Test in Task 4.
4. **Same variant on two lines** (different line item properties): "In cart" means any line has the variant; the difference check compares by line `key`, not by variant. Tests in Tasks 6 and 7.
5. **The theme reads the response body after the widget**: the theme must still get the full, unread body. Test in Task 5.

### Task 4: Cart store with a serial write queue

**Files:**
- Create: `chat-widget/src/cart/store.ts`
- Test: `chat-widget/src/cart/store.test.ts`

**Interfaces:**
- Consumes: `CartApi`, `Cart`, `WriteResult`, `CartError` (Task 2), `ThemeAdapter` (Task 3).
- Produces:

```ts
export type CartState = {
  cart: Cart | null;
  pending: string | null;                          // variant GID or line key being written
  error: { key: string; message: string } | null;
};
export type CartStore = {
  getSnapshot(): CartState;                        // same object until the state changes
  subscribe(listener: () => void): () => void;
  load(): Promise<void>;                           // first /cart.js read, no theme refresh
  add(variantGid: string, quantity: number): Promise<void>;
  setQuantity(lineKey: string, quantity: number): Promise<void>;
  themeWrote(cart: Cart | null): void;             // from intercept: null means "re-read"
  refresh(withTheme: boolean): Promise<void>;      // from catch-up
};
export function createCartStore(deps: {
  api: CartApi; adapter: ThemeAdapter; onLocalChange: () => void; failMessage: string;
}): CartStore;
```

Behaviour:
- `add` and `setQuantity` go into one promise-chain queue.
- Each queued write sets `pending` to its key. On success it calls `adapter.apply(sections)` and then sets the cart, in the same synchronous block, then calls `onLocalChange()`.
- On failure it sets `error` to `{ key, message }`, where the message is the `CartError` message or `failMessage` for any other error. It then does a `refresh(false)`. The queue moves on either way.
- A new write for a key clears that key's error.
- `themeWrote` while the queue is busy only marks the store dirty. When the queue drains, the store does one `refresh(false)`. When the queue is idle, it adopts the cart, or re-reads when given `null`, then calls `onLocalChange()`.
- `refresh(withTheme)` reads `/cart.js`. If `cartsDiffer` (Task 6 makes it a public export; define it here and re-export from `catchup.ts`) returns true, it sets the cart, and when `withTheme` it also runs `adapter.apply(await api.renderSections(adapter.sections))` before setting the cart. It never calls `onLocalChange`.

- [ ] **Step 1: Write the failing tests** with a fake `CartApi` whose calls resolve through deferred promises, and a spy adapter that records the order of `apply` and the store snapshot's cart:
  - `three setQuantity calls run one at a time, in order`: the second `api.change` is not called until the first resolves.
  - `a write applies sections before the cart is published`: when `apply` is called, `getSnapshot().cart` is still the old cart; after the write resolves, it is the new one. `onLocalChange` is called once.
  - `a refused write keeps the cart, records the error and the queue continues`: the first change rejects `new CartError("Only 2 left", 422)`, the second resolves. The cart equals the second result, and `error` was `{ key: "k1", message: "Only 2 left" }` after the first. `getCart` was called once, for the refresh after the failure.
  - `a non-CartError failure uses failMessage`.
  - `themeWrote during a write reconciles once after the queue drains`: two `themeWrote(cart)` calls during an in-flight write lead to exactly one `getCart` after it resolves.
  - `themeWrote(null) while idle re-reads; themeWrote(cart) while idle adopts without a request`.
  - `refresh(true) renders sections only when the cart changed`.
  - `getSnapshot returns the same object when nothing changed`.
  - `a failed load leaves cart null and does not reject; the first successful write fills it`.

### Task 5: Intercept theme cart writes

**Files:**
- Create: `chat-widget/src/cart/intercept.ts`
- Test: `chat-widget/src/cart/intercept.test.ts`

**Interfaces:**
- Consumes: `Cart` (Task 2).
- Produces:

```ts
export type CartWrite = "add" | "write";
export function cartWriteKind(url: string, root: string, origin: string): CartWrite | null;
export function installIntercept(
  win: { fetch: typeof fetch; XMLHttpRequest: typeof XMLHttpRequest },
  root: string, origin: string,
  onWrite: (kind: CartWrite, cart: Cart | null) => void,
): typeof fetch; // returns the ORIGINAL fetch, for the store's api
```

Behaviour:
- `cartWriteKind` resolves `url` against `origin`. A different origin gives `null`. It strips `root`, then matches `^cart/(add|change|update|clear)(\.js)?$`: `add` gives `"add"`, the rest give `"write"`.
- The fetch wrapper calls the original fetch, returns that same `Response` to the caller, and in a detached `try/catch` reads `response.clone().json()`:
  - For `"write"` it parses into `onWrite("write", body)` when `body.items` is an array. In any other case, including a JSON error, it calls `onWrite(kind, null)`.
  - For `"add"` it always calls `onWrite("add", null)`.
- The XHR wrapper patches `open` to remember the URL and listens for `load` to do the same on `responseText`.
- Calls are only made for `2xx` statuses.
- A guard property `__chatCartIntercept` on `win` makes the second install return the saved original without wrapping again.

### Task 9: Standard-events theme adapter, adapter selection and docs

> Amended 2026-10-20 after reading the live theme. The dev store `ranger-ngiknsha` runs Shopify's **Horizon** theme. Horizon's cart icon and cart drawer refresh themselves when a `shopify:cart:lines-update` event (Shopify standard storefront events, `https://cdn.shopify.com/storefront/standard-events.js`) is dispatched on `document`; swapping their `innerHTML` would fight Horizon's own morph/hydration. The user approved replacing the Ranger HTML-swap adapter with a broadcast adapter that is the default for every theme.

**Interfaces:**
- Changes in `theme.ts`:

export type ThemeUpdate = { cart: Cart; sections: Sections };

- `store.ts` calls `adapter.sections()` (at call time, not once) everywhere it used `adapter.sections`, and `adapter.apply({ cart, sections })` with the cart it is about to publish. `refresh(true)` passes the cart it read.
- Produces in `standardEvents.ts`:

```ts
export const CART_LINES_UPDATE = "shopify:cart:lines-update";
export function toStandardCart(cart: Cart): StandardCart; // port of the module's createCartFromAjaxResponse

```

  - `toStandardCart`: `{ id: "gid://shopify/Cart/" + token, totalQuantity: item_count, cost: { totalAmount: { amount, currencyCode } }, lines: items.map(i => ({ id: "gid://shopify/CartLine/" + key, quantity, cost: { totalAmount: { amount, currencyCode } } })), discountCodes: [] }`. `amount` is cents / 100 as a plain decimal string with the currency's minor digits (e.g. `"129.00"`, `"1500"` for JPY).
  - `standardEventsAdapter.sections()` returns the unique `data-section-id` values of `cart-items-component[data-section-id]` elements on the page.
  - `standardEventsAdapter.apply({ cart, sections })` dispatches on `document`: `Object.assign(new Event(CART_LINES_UPDATE, { bubbles: true, cancelable: true }), { action: "update", context: "chat", lines: cart.items.map(i => ({ id: "gid://shopify/CartLine/" + i.key, quantity: i.quantity })), promise: Promise.resolve({ cart: toStandardCart(cart), detail: { sections, itemCount: cart.item_count } }) })`. It never uses `action: "add"`: Horizon auto-opens its drawer on adds, and the shopper chose a silent theme refresh. Dispatch errors are caught.
